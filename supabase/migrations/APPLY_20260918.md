# Applying 20260918000000_creator_portal_fixes.sql

**Apply this migration BEFORE deploying the matching frontend.** Order matters
more than usual here.

The new UI writes columns this migration creates (`sales_commission_rate`,
`manager_commission_rate`, `show_client_cpm`, `campaign_creators.status` …).
Against the old schema those writes are refused with `PGRST204`. The UI now says
so in plain words instead of failing silently, but the affected actions still
will not work until the migration is in:

- creating a campaign
- changing a commission rate or the client CPM switch
- a creator applying to a campaign
- a manager picking / releasing creators

The other direction is safe: the migration can sit in production under the
**old** frontend indefinitely. Every new column has a default that reproduces
today's behaviour (30% sales rate, inherited manager rate, CPM hidden from
clients, existing assignments `Approved`).

## Is it applied?

```bash
npm run db:migrate -- --status
```

Read-only; answers from Postgres itself. Exit code 0 means applied. The owner's
*System Config → Database* page shows the same two rows once the new frontend
is deployed.

## How to apply it

The file is **one transaction** and **idempotent**: a failure changes nothing,
and running it twice is harmless.

### Do NOT use `supabase db push`

Two reasons, both specific to this project:

1. On 2026-09-18 it failed before touching the database:
   `unexpected login role status 403 … does not have the necessary privileges`.
   Recent CLI versions start `db push` by creating a temporary login role
   through Supabase's **Management API**, which needs Owner/Administrator on
   the organisation that owns the project. The project belongs to a different
   organisation from the CLI login, so that call is refused.
2. Even with the right role it is the wrong tool here. Every earlier migration
   was applied by pasting into the SQL Editor (see `APPLY_20260821.md`,
   `APPLY_20260822.md`), so the migration-history table does not list them.
   `db push` would try to replay all of them from the start. The [README](README.md)
   records a 2026-09-04 `db push` that began by trying to undo the security
   hardening on production.

### Option A — one file over a direct connection (recommended)

`supabase db query` runs a single SQL file straight against Postgres. No
Management API, no history table, no organisation role needed — only the
**database password** (Supabase dashboard → *Project Settings → Database*; it
can be reset there if nobody has it).

```bash
npx supabase db query \
  --db-url "postgresql://postgres.aglikzyarmqbdmjvkvyj:<PASSWORD>@aws-1-us-east-1.pooler.supabase.com:5432/postgres" \
  --file supabase/migrations/20260918000000_creator_portal_fixes.sql
```

- The host, user and port above are what `supabase link` recorded for this
  project (`supabase/.temp/pooler-url`). Port **5432** is the session pooler;
  use it, not 6543.
- The password must be **percent-encoded** if it contains characters such as
  `@`, `#`, `/`, `%` or `:`. In Node: `encodeURIComponent('the password')`.
- Put the command in a terminal, not in a chat, a ticket or a commit.

Then confirm:

```bash
npm run db:migrate -- --status
```

### Option B — Supabase SQL Editor

For someone who is a member of the project's organisation with SQL Editor
access (Developer or above): open the project → **SQL Editor** → paste the
whole file → **Run**. NOTICE output is informational.

## What it depends on

It assumes these are already applied (it replaces functions they created and
adds policies alongside theirs):

- `20260822000003_campaign_creators.sql` — the junction table and its two mirror triggers
- `20260822000005_tenant_policy_reset.sql` — `current_user_role()` and the scoped policies
- `20260530000000_payout_system.sql` — `get_my_payout_role()`, `is_payment_manager()`

If one is missing the transaction fails with a clear "function … does not
exist" and nothing is changed.

## Verified by

```bash
node tests/creator-portal-fixes.test.cjs
```

which runs `supabase/migrations/__tests__/creator-portal-fixes.test.cjs`: the
real migration chain on real Postgres (PGlite), every assertion executed as the
`authenticated` role so RLS is genuinely enforced. It covers the cases that
matter if this goes wrong — a creator approving themselves, a manager raising
their own commission, one tenant's manager approving another tenant's work.

## Rolling back

Nothing here is destructive, so a rollback is only needed if the policies
themselves cause trouble. The columns can stay. To restore the previous
behaviour of the mirror triggers, re-run the two `CREATE OR REPLACE FUNCTION`
blocks from `20260822000003_campaign_creators.sql` — but note that doing so
with `Applied` rows present will put those applicants straight onto their
campaigns, which is the defect this migration exists to remove. Clear or
resolve pending applications first.
